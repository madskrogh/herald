# Limits

Every number and limit the spec's requirements name, with what it limits and the reason for its value. A requirement names a limit by its name instead of repeating the value.

| Limit | What it limits | Value | Reason |
|-------|----------------|-------|--------|
| `attempt-timeout` | How long an Endpoint has to answer an Attempt, from the Attempt's start | 15 s | Long enough for a slow handler that does its work before answering, and it caps how long one Endpoint holds a worker. |
| `max-attempts` | How many Attempts Herald makes for one Delivery before it fails | 8 | With `retry-delays`, Attempts span about a day. |
| `retry-delays` | The delay before each retry of a failed Attempt, after the 1st to the 7th Attempt fails | 5 s, 1 m, 10 m, 1 h, 3 h, 6 h, 12 h | The early delays are short, so a brief failure recovers in seconds; the later ones are long, so an Endpoint that is down for up to a day (about 22 h in all) still gets its Messages. |
| `retry-jitter` | How far each of `retry-delays` may vary | 10% either way | Keeps Deliveries that failed together from all retrying at the same moment. |
| `retry-scale` | How far `HERALD_RETRY_SCALE` may shrink every one of `retry-delays`, and its jitter | a factor in (0, 1]; 1 when not set | The setting exists to run the whole schedule in seconds on a local stack and in the end-to-end tests, so it only shrinks (#16). |
| `max-delay` | How long a Message may wait for its handoff, and an Attempt to start once due, when no fault affects it | 2 s | Neither waits for anything but Herald noticing it, so a delay of seconds means a stall. Tight enough to catch one, with room for a busy machine: one run measured at most 0.5 s (#80). It doesn't depend on `retry-scale`. |
| `max-delay-in-fault` | The same, while NATS is unavailable, Postgres is slowed or a dispatcher restarts | 15 s | Loose enough that only a stall breaks it, not the fault itself: one run measured up to 5.9 s under a fault (#80). Not one limit per fault, since timing under a slowed Postgres depends on the machine. |
| `fault-nats-unavailable` | How long NATS is unavailable in the fault R-73 names | 5 s | Long enough that the relay tries to hand off, and fails, while NATS is unavailable. |
| `fault-postgres-cpu` | The share of one CPU Postgres has in the fault R-74 names | 1% | Little enough that a Delivery's first Attempt comes seconds late, so the fault shows; a tenth of a CPU barely shows. |
| `max-in-flight-per-endpoint` | How many Attempts to one Endpoint may be in flight at once, across all dispatchers | 4 | Limits the load Herald puts on a slow Endpoint, and how many of a dispatcher's workers one Endpoint can take. |
| `response-body-kept` | How much of an Endpoint's response body Herald keeps with each Attempt | 4 KiB | Enough for an error message, and it bounds the storage each Attempt takes. |
| `retention` | How long Herald keeps a Delivery and its Attempts | 30 days | A month of history is enough to inspect and replay Deliveries, and it bounds storage. |
| `secret-overlap` | How long an Endpoint's previous signing secrets stay valid after a rotation | 48 h | Longer than a Delivery's retry schedule, so a Delivery that carries only the old secret still verifies. |
| `idempotency-window` | How long an Idempotency-Key holds the Message it was first sent with | 24 h | A client retries a failed request within hours, not days. |
| `idempotency-key-bytes` | The longest Idempotency-Key | 256 | A key needs a cap, to stay within what the database's unique index holds; 256 is a round number well inside it. |
| `max-payload` | The largest Message payload | 256 KiB | A Message is a notification, not a way to move bulk data. |
| `max-request-body` | The largest request body over REST | 1600 KiB | Six times `max-payload`, since each payload byte may be escaped as `\u00XX` in the JSON string that carries it, plus 64 KiB for the other fields. |
| `event-type-bytes` | The longest Event type | 128 | An Event type needs a cap, since every Delivery handed off carries one; 128 is a round number with headroom. |
| `filter-pattern-bytes` | The longest pattern in an Endpoint's filter | 128 | Equal to `event-type-bytes`, so a filter can name every Event type. |
| `max-filter-patterns` | How many patterns an Endpoint's filter may hold | 32 | A filter needs a cap, since it is matched on the request path; 32 is a round number with headroom. |
| `max-endpoints-per-application` | How many Endpoints one Application may have | 100 | A Message's Deliveries are handed off together, in one NATS message of at most 1 MB ([ADR 0002](../docs/adr/0002-two-services-outbox-nats-handoff.md)), and each carries its Endpoint's URL and signing secrets. With a 256 KiB payload, about 350 would fill it; 100 leaves a margin. |
| `signing-secret-bytes` | The size of the random key in a signing secret | 24 | The smallest key Standard Webhooks allows. |
| `endpoint-url-bytes` | The longest Endpoint URL | 2048 | The length most clients and servers accept. |
| `application-name-bytes` | The longest Application name | 256 | A name needs a cap; 256 is a round number with headroom. |
| `max-page-size` | The most results one page of a list call returns | 100 | Bounds the size of one list response. |
| `max-api-latency` | How long a Tenant API call may take, from the Tenant sending it to receiving the response, when no fault slows Postgres | 100 ms | A Tenant calls the Tenant API inside its own request handling, so a call costs its users time. One scenario run measured at most 21 ms with no fault, 5 ms with NATS unavailable and 6 ms during a dispatcher restart (#114); 100 ms leaves room for a busy machine and catches a call that slows several-fold. |
| `max-api-latency-in-fault` | The same, while Postgres is slowed | 15 s | Every call waits on Postgres, so a slowed Postgres slows every call: one run measured up to 8.5 s at `fault-postgres-cpu` (#114). Loose enough that only a stall breaks it, as for `max-delay-in-fault`. |
| `max-service-memory` | How much memory a service may use while the scenario runs, as its container's memory | 32 MiB | One run measured a peak of 16 MiB for herald-api and 11 MiB for herald-dispatcher (#114); twice the larger leaves room for a busy run and still catches memory that grows with the traffic. |
| `memory-settle-time` | How long after the scenario ends a service's memory is measured at rest | 3 min | A runtime may hand freed memory back to the operating system some time after it is freed; one run was steady within 3 minutes of the scenario ending (#114). |
| `memory-at-rest-margin` | How far above its level before traffic a service's memory may be at rest | 8 MiB | One run measured 5 MiB above for herald-api and 2.5 MiB for herald-dispatcher (#114); about twice that catches a leak of a few MiB per run without failing a correct build. |
| `max-db-connections` | How many connections to Postgres one service process may hold at once | 8 | Every replica draws on Postgres's one connection limit, so each process needs a cap an operator can plan for. No measurement backs 8: one scenario run saw at most 7 (#114), and the load test settles it (#82). Today the services' pool grows with the CPU count, so meeting the cap is a code change. |
| `max-attempts-in-flight` | How many Attempts one herald-dispatcher process may have in flight at once | 32 | A guess no measurement backs; the load test settles it (#125). It caps the connections one dispatcher opens to Endpoints. |
| `lease-duration` | How long a Delivery whose dispatcher stopped mid-Attempt, without recording it or giving it back, waits from the Attempt's start before it is due again | 60 s | Well above `attempt-timeout`, so a dispatcher that is still running and can reach Postgres records its Attempt first; one that has lost Postgres for longer may see its Attempt made again, as R-17 allows. Short enough that a Delivery stranded by a dispatcher that died is retried within a minute. |
| `max-resume-delay` | How long Herald may take to resume handoff and Attempts once Postgres and NATS are both reachable again | 45 s | Herald retries a failing dependency less often the longer it fails, at most 30 s apart, so a long outage doesn't fill the logs or load the dependency as it recovers. The rest leaves time to reconnect and run a round once it is back (#114). |
| `dependency-log-interval` | The longest a service goes without logging an error while Postgres or NATS is unreachable | 1 min | Often enough that an operator watching the logs sees the outage is still on, rare enough that a long outage doesn't flood them (#114). |
| `max-shutdown` | How long a service may take to exit once told to stop | 9 s | Docker and Kubernetes wait 10 s before killing a container, so a service that takes longer is killed mid-shutdown; the second left over is margin for the process to exit. |
| `attempt-drain-timeout` | How long the Attempts in flight get to finish once a dispatcher is told to stop | 5 s | Leaves time, within `max-shutdown`, to cut off the Attempts still running and give their Deliveries back. |
| `rest-header-timeout` | How long a REST client may take to send a request's headers | 10 s | Bounds how long a slow or stalled client holds a connection. No measurement backs the value; any of a few seconds to a minute serves (#114). |
| `rest-read-timeout` | How long a REST client may take to send a whole request | 30 s | As for `rest-header-timeout`, and enough to send `max-request-body` over a slow link. |
| `rest-idle-timeout` | How long herald-api keeps an idle REST connection open | 2 min | As for `rest-header-timeout`: long enough to reuse a connection between a Tenant's calls, short enough that idle clients don't pile up connections. |
| `keyring-key-id-bytes` | The longest key ID in `HERALD_KEYRING` | 255 | Each encrypted signing secret starts with its key ID's length, in one byte. |
