# Postgres column list

The Postgres columns the scenario writes, to set up a run, and reads, for where the run left its Messages and Deliveries ([R-84](storage.md#r-84--implemented) and [R-85](storage.md#r-85--implemented)). Herald's migrated database is checked against this file, and the scenario's harness reads only these columns. They are here only until something else shows the scenario what it needs ([What Herald stores](storage.md)).

`Type` is the column's type as Postgres names it. `Null` says whether the column may be NULL: `allowed` or `never`. `Set by` says who writes the column: `scenario`, which writes it to set up a run; `database`, which Postgres generates when the scenario writes a row without it, and the scenario reads back; or `Herald`, whose services write it and the scenario only reads. `Holds` is what each value must mean, and `Why` is what the scenario uses it for. `Leaves when` names what replaces the column: once it exists, the scenario writes or reads through it instead, and the column leaves the list.

## Columns

| Table | Column | Type | Null | Set by | Holds | Why | Leaves when |
|---|---|---|---|---|---|---|---|
| `ingest.tenants` | `id` | uuid | never | database | The Tenant's ID: the one its spans carry as `herald.tenant_id`. | The scenario creates its Tenant without an ID, and finds the run's Messages and spans by the one Postgres generates. | herald-admin's commands are requirements, and the scenario creates its Tenant through them. |
| `ingest.tenants` | `name` | text | never | scenario | Writing a row with a name creates a Tenant. | The scenario creates a Tenant of its own for each run, as herald-admin does ([ADR 0009](../docs/adr/0009-herald-admin-writes-ingest-directly.md)), so the run's Messages are the only ones it reads. | herald-admin's commands are requirements, and the scenario creates its Tenant through them. |
| `ingest.api_keys` | `tenant_id` | uuid | never | scenario | The `id` of the Tenant the key acts for. | The scenario gives its Tenant an API key, as herald-admin does. | herald-admin's commands are requirements, and the scenario creates its API key through them. |
| `ingest.api_keys` | `key_hash` | bytea | never | scenario | The SHA-256 of a key Herald issued ([R-22](tenant-api.md#r-22--implemented)). A row here issues that key, whatever its form, so the Tenant API accepts it for the row's Tenant ([R-21](tenant-api.md#r-21--implemented)). | The scenario calls the Tenant API as its Tenant, with a key it makes itself. | herald-admin's commands are requirements, and the scenario creates its API key through them. |
| `ingest.messages` | `id` | uuid | never | Herald | The Message ID the Tenant API returned. | The scenario tells the Messages it sent from any it didn't ([R-38](tenant-api.md#r-38--implemented)). | An API lists a Tenant's Messages, with whether each was handed off or Parked. |
| `ingest.messages` | `tenant_id` | uuid | never | Herald | The `id` of the Message's Tenant. | The scenario reads every Message of its Tenant, so that one it didn't send shows. | An API lists a Tenant's Messages, with whether each was handed off or Parked. |
| `ingest.messages` | `handed_off_at` | timestamp with time zone | allowed | Herald | Set once the Message is handed off, and NULL until then. Only whether it is set is read. | Every Message the scenario sends is handed off by the end of the run ([R-1](delivery.md#r-1--implemented)). | An API lists a Tenant's Messages, with whether each was handed off or Parked. |
| `ingest.messages` | `parked_at` | timestamp with time zone | allowed | Herald | Set once the Message is Parked ([R-59](delivery.md#r-59--implemented)), and NULL otherwise. Only whether it is set is read. | The scenario sends no Message a dispatcher refuses, so none may be Parked. | An API lists a Tenant's Messages, with whether each was handed off or Parked. |
| `delivery.deliveries` | `id` | uuid | never | Herald | The Delivery's ID: the one its Attempts' spans carry as `herald.delivery_id`. | The scenario counts the Attempts Herald recorded for each Delivery, and finds them in its spans. | The Delivery API returns a Message's Deliveries. |
| `delivery.deliveries` | `message_id` | uuid | never | Herald | The Message ID the Tenant API returned. | The scenario finds the Deliveries of each Message it sent. | The Delivery API returns a Message's Deliveries. |
| `delivery.deliveries` | `endpoint_id` | uuid | never | Herald | The Endpoint ID the Tenant API returned. | With `message_id`, it says which Endpoint each Delivery is for, so the scenario finds one Delivery for each Endpoint whose filter matches, and none for any other (R-1). | The Delivery API returns a Message's Deliveries. |
| `delivery.deliveries` | `state` | text | never | Herald | `pending`, then `succeeded` or `failed` ([R-9](delivery.md#r-9--implemented), [R-12](delivery.md#r-12--implemented), [R-13](delivery.md#r-13--implemented)). | The scenario waits until no Delivery is pending, then checks that each ended as its Endpoint's answers say. | The Delivery API returns a Message's Deliveries. |
| `delivery.attempts` | `delivery_id` | uuid | never | Herald | One row for each Attempt Herald recorded, with the `id` of its Delivery. | The scenario checks that no Delivery has more Attempts recorded than `max-attempts` (R-12), and that each recorded Attempt has its span. | The Delivery API returns a Delivery's Attempt history. |
