# Standard Webhooks for signing

Herald signs every Attempt following the Standard Webhooks spec (standardwebhooks.com): `webhook-id`, `webhook-timestamp` and `webhook-signature` headers, with HMAC-SHA256 and a separate secret for each Endpoint. Receivers can verify with existing libraries in any language, so Herald ships no receiver library, and the timestamp lets receivers reject replayed requests. The secrets must be readable in order to sign, so they are encrypted at rest with AES-GCM rather than hashed. Every ciphertext carries the ID of the key that encrypted it, and the services load a keyring of current and older keys from config, so the encryption key can be rotated without downtime. Re-encrypting existing secrets after a key rotation is deferred.

Signing secrets can be rotated in v1. An Endpoint holds a list of signing secrets, each with an optional expiry. Rotating adds a new secret and gives the previous one a 48-hour expiry, which is longer than the 24-hour retry window, so in-flight Deliveries that carry only the old secret still verify. Deliveries are signed with every secret that hasn't expired (the spec allows several signatures in one header). Replays are signed with the Endpoint's current secrets, which herald-api attaches to the replay request.
